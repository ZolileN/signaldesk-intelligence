
SIGNALDESK AFRICA
BUILDABLE ENGINEERING SPECIFICATION
Version: 1.0Status: Foundational Engineering SpecificationArchitecture: Event-driven intelligence platformPrimary Objective: Convert fragmented information into evidence-backed intelligence about developing situations and customer exposure.

1. SYSTEM CONTRACT
Every external source must ultimately produce an:
Observation
Every observation may produce:
Claims
Entities
Events
Multiple events may form:
Situation
A situation may create:
Exposure
An exposure may produce:
Impact
An impact may produce:
Recommendation
The canonical pipeline is:
SOURCE
  ↓
OBSERVATION
  ↓
PROCESSING
  ↓
CLAIM
  ↓
ENTITY
  ↓
EVENT
  ↓
SITUATION
  ↓
TRAJECTORY
  ↓
EXPOSURE
  ↓
IMPACT
  ↓
RECOMMENDATION

The original observation must remain immutable.
Derived AI interpretations can change. The original source evidence must not.

22. THE EIGHT-QUESTION API CONTRACT
Every situation must be able to produce answers to:
1. What is happening?
2. Is it getting worse or better?
3. Where is it happening?
4. Who is involved?
5. What is driving it?
6. What happens next?
7. How am I exposed?
8. What should I do?
The API response should therefore expose:
{
  "situation_id": "uuid",

  "what_is_happening": {
    "summary": "...",
    "evidence": []
  },

  "trajectory": {
    "direction": "ESCALATING",
    "score": 0.82,
    "explanation": "..."
  },

  "where": {
    "locations": []
  },

  "actors": [],

  "drivers": [],

  "potential_next_developments": [],

  "exposure": {
    "level": "HIGH",
    "assets": [],
    "explanation": "..."
  },

  "recommended_actions": []
}
This is the core product contract.

26. AI MODEL CONTRACT
AI models should not directly modify the database without validation.
The correct pipeline is:
AI MODEL
   ↓
STRUCTURED OUTPUT
   ↓
SCHEMA VALIDATION
   ↓
BUSINESS VALIDATION
   ↓
DATABASE WRITE
Example:
{
  "entity_mentions": [
    {
      "text": "Company X",
      "entity_type": "COMPANY",
      "confidence": 0.94
    }
  ]
}
If the model returns malformed output:
REJECT
   ↓
RETRY
   ↓
FALLBACK MODEL
   ↓
HUMAN REVIEW

28. THE SITUATION ENGINE
The Situation Engine is the heart of SignalDesk.
Its responsibility is to determine:
Are these events related?
The engine should use:
Semantic similarity
Temporal proximity
Geographic proximity
Entity overlap
Causal relationships
Event types
Narrative similarity
Conceptually:
Situation Similarity =
Semantic Similarity
+
Entity Overlap
+
Geographic Proximity
+
Temporal Proximity
+
Causal Relationship
If the score exceeds a threshold:
NEW EVENT
     ↓
EXISTING SITUATION
Otherwise:
NEW EVENT
     ↓
NEW SITUATION

29. SITUATION UPDATE LOGIC
Every new event should trigger:
1. Find related situations
2. Score similarity
3. Attach event if related
4. Recalculate severity
5. Recalculate trajectory
6. Recalculate actors
7. Recalculate geography
8. Recalculate drivers
9. Recalculate customer exposure
10. Evaluate alerts
This is the central intelligence loop.

30. TRAJECTORY ENGINE
The trajectory engine should not depend solely on an LLM.
It should calculate measurable signals:
event_frequency_change
severity_change
actor_count_change
geographic_spread_change
institutional_response_change
narrative_volume_change
Example:
Last 7 days:
Events: 4

Current 7 days:
Events: 17

Event growth:
+325%
This is a measurable escalation signal.
The LLM can then explain the result.

37. MVP SUCCESS CRITERIA
The MVP is successful if:
A source publishes information
        ↓
SignalDesk processes it
        ↓
The system identifies an event
        ↓
The system connects related events
        ↓
A situation is created
        ↓
The situation evolves over time
        ↓
The system answers the eight questions
The most important test is:
Can an analyst understand a developing situation faster and more accurately using SignalDesk than by manually monitoring multiple news sites, radio stations, social media platforms and documents?
That is the real product test.

38. FINAL ENGINEERING PRINCIPLE
SignalDesk should not be built as:
AI chatbot
+
News scraper
+
Radio player
It should be built as:
CONTINUOUS OBSERVATION
        ↓
STRUCTURED EVIDENCE
        ↓
ENTITY GRAPH
        ↓
EVENT GRAPH
        ↓
SITUATION GRAPH
        ↓
TRAJECTORY
        ↓
EXPOSURE
        ↓
DECISION SUPPORT
The fundamental technical moat is not the individual AI model.
The moat is the continuously updated:
African intelligence graph of sources, entities, events, situations, relationships, trajectories and outcomes.
That is what makes the architecture defensible.
