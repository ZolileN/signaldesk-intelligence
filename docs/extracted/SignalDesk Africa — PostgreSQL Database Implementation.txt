
SignalDesk Africa — PostgreSQL Database Implementation
0. Target Stack
PostgreSQL 16+
PostGIS
pgvector
citext
pgcrypto

Recommended database architecture:
PostgreSQL
├── Relational system of record
├── PostGIS spatial intelligence
├── pgvector semantic search
├── JSONB flexible metadata
└── Outbox event publishing

The database is not merely a storage layer. It is the canonical intelligence graph:

   ↓

   ↓

   ↓
Entities
   ↓

   ↓

   ↓

   ↓

2. Migration 001 — Extensions
CREATE EXTENSION IF NOT EXISTS postgis;
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS citext;
CREATE EXTENSION IF NOT EXISTS pgcrypto;

Why each extension exists
Extension
Purpose
postgis
Geographic locations, radius searches, spatial exposure
vector
Embeddings and semantic similarity
citext
Case-insensitive email and text comparison
pgcrypto
UUID generation

3. Migration 002 — Database Schema
CREATE SCHEMA IF NOT EXISTS signaldesk;

SET search_path TO signaldesk, public;

All SignalDesk tables should live under:
signaldesk.*

This prevents collisions with other applications sharing the same PostgreSQL instance.

Organisations

    name TEXT NOT NULL,

    metadata JSONB NOT NULL DEFAULT '{}',

);

CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()

CREATE TABLE organisation_members (
    organisation_id UUID NOT NULL

        ON DELETE CASCADE,

This provides multi-tenancy from day one.

7. Migration 006 — Observations
An observation is the original captured information.
CREATE TABLE observations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    source_id UUID NOT NULL
        REFERENCES sources(id)
        ON DELETE RESTRICT,

    content_type content_type NOT NULL,

    title TEXT,

    raw_content TEXT,

    transcript TEXT,

    source_url TEXT,

    published_at TIMESTAMPTZ,

    captured_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    language_code TEXT,

    country_code CHAR(2),

    location GEOGRAPHY(POINT, 4326),

    content_hash TEXT NOT NULL UNIQUE,

    storage_reference TEXT,

    processing_status processing_status
        NOT NULL DEFAULT 'PENDING',

    metadata JSONB NOT NULL DEFAULT '{}',

    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

Important principle
The observation is immutable.
The system should never overwrite:
What was actually captured?

Instead, AI interpretations are stored separately.

Audio Segments
CREATE TABLE audio_segments (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    observation_id UUID NOT NULL
        REFERENCES observations(id)
        ON DELETE CASCADE,

    segment_start TIMESTAMPTZ NOT NULL,

    segment_end TIMESTAMPTZ NOT NULL,

    audio_reference TEXT NOT NULL,

    duration_seconds NUMERIC(10,3),

    codec TEXT,

    sample_rate INTEGER,

    channels INTEGER,

    content_classification TEXT,

    classification_confidence NUMERIC(5,4),

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    CHECK (
        segment_end > segment_start
    )
);

This supports the SignalDesk radio architecture:
Radio stream
    ↓
Audio segment
    ↓
Speech recognition
    ↓
Observation

Example:

+40%

18. Migration 017 — Outbox
SignalDesk should use the Transactional Outbox Pattern.
CREATE TABLE outbox_events (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    event_type TEXT NOT NULL,

    aggregate_type TEXT NOT NULL,

    aggregate_id UUID NOT NULL,

    payload JSONB NOT NULL,

    published_at TIMESTAMPTZ,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

Example:
Transaction:
Create Event

Same Transaction:
Create outbox_events row

Worker:
Reads outbox_events
        ↓
Publishes EventDetected
        ↓
Marks published_at

This prevents the classic problem:
Database write succeeded
BUT
message queue publish failed

Important implementation note
vector(1536) assumes the selected embedding model produces 1,536-dimensional vectors.
If the chosen embedding model has a different dimensionality, the schema must be changed consistently.

My recommendation
For the first implementation, do not build the entire database at once.
Build the first vertical slice:
VectaNews
    ↓
Observation
    ↓
Entity Extraction
    ↓
Event Detection
    ↓
Situation Creation
    ↓
Eight-Question Situation API

The minimum production-worthy core is:

entities
entity_mentions
claims

event_observations
event_entities
situations
situation_events
situation_entities
situation_trajectory_snapshots

Then add:
customer_assets
exposures
alerts
recommendations

once the core intelligence graph is functioning.
The crucial architectural decision is that the database schema must be built around the Situation, not around articles, radio broadcasts or news stories. Those are merely sensors. The durable asset is the continuously evolving intelligence model of what is happening in the world.
